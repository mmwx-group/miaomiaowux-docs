The MeowX client (iOS / macOS / Android / Windows / OpenWrt) can sign in with a panel account directly. Once signed in, the client lists every subscription under the account and imports one with a single tap. When nodes or subscriptions change in the panel, the client syncs automatically, so there is no need to copy subscription links by hand.

You can also use a subscription without signing in: just paste the subscription link into the client. That route does not need any of the conditions in "What the master needs first" below.

This page covers the admin's preparation first, then how users sign in, and finally troubleshooting. For downloading and installing the client see [Client Download](/docs/en/client-download); for its settings see [Client Settings](/docs/en/client-settings).

## What the master needs first

The client talks to the master over a dedicated encrypted channel (see [Security model](#security-model) below), not the web login. That channel can only be established with the master's **client identity certificate**: **if the master has no certificate, the client cannot sign in by any method**, including username and password.

The master requests the certificate from the license service automatically. The admin only needs to make sure of these four things:

| Requirement | Where | Notes |
| --- | --- | --- |
| Master server address is set | System Settings → "System" → "Master server address" | Use the public HTTPS domain, e.g. `https://panel.example.com`. The certificate is bound to this domain and the client only connects to it. See [Master Domain](/docs/en/domain-master) |
| License is activated | System Settings → "License" | The license service issues the certificate. A master without an activated license has no client sign-in (subscription links are unaffected) |
| Domain not claimed by another license | — | A domain can be bound to only one license. You may hit this after switching licenses or lending the domain to another master; use another domain or contact support to unbind it |
| `/api/secure/*` is reachable from outside | Reverse proxy / CDN / tunnel | The client uses `/api/secure/cert`, `/api/secure/rpc` (binary POST) and `/api/secure/ws` (WebSocket). All three must reach the master from the internet over HTTPS on port 443 |

### Why HTTPS on port 443 is required

The QR code / login link generated by the web panel always writes the master address as `https://` plus the certificate domain, **with no port**. So the client always connects to `https://your-domain` (port 443):

- If the master server address is `http://` or uses a port other than 443, QR sign-in cannot connect.
- When the master sits behind Nginx, Cloudflare or a [Cloudflare Tunnel](/docs/en/cloudflare-tunnel), make sure port 443 on that domain reaches **every path** of the master, not just the subscription paths. WebSocket must be allowed too, otherwise real-time sync won't arrive after sign-in.
- Don't fill in only the "subscription domain" and leave the master server address empty: the subscription domain is often a CDN that proxies only subscription paths, so the certificate gets issued for it and the client then can't find `/api/secure/*` there.

### Issuance and renewal

Nothing to do manually:

- The certificate is issued the first time a client (or the web QR sign-in dialog) asks for it, and is valid for 30 days.
- The master starts checking 2 minutes after startup and then every 6 hours, renewing when fewer than 5 days remain. If renewal fails while the old certificate is still valid, the old one keeps being used.
- After a failed issuance the master retries automatically, backing off from 30 seconds up to 30 minutes. After fixing a setting, wait at most that long, or restart the master to retry immediately.

### Checking that the certificate is OK

Open `https://your-domain/api/secure/cert` in a browser:

| What you see | Meaning |
| --- | --- |
| JSON containing `domain`, `masterPub`, `expireUnix` | Certificate OK; `domain` should match the master server address |
| `{"error": "..."}` | The master has no certificate; the reason is in `error`, see [Troubleshooting](#troubleshooting) |
| An HTML page, 404 or a Cloudflare block page | The request never reached the master: the reverse proxy / tunnel isn't passing `/api/secure/*` |

Another quick check: as an admin, open the avatar menu at the top right of the panel → "QR login". If the certificate has a problem, the dialog says the master has no usable client identity certificate, gives the reason, and doesn't generate a QR code.

## Sign-in methods

Five methods; pick one by device:

| Method | Starts from | Best for | 2FA code needed |
| --- | --- | --- | --- |
| [Account sign-in](#account-sign-in) | Enter master address, username, password in the client | All platforms | Yes, if 2FA is on |
| [QR sign-in](#qr-sign-in) | Web panel shows a QR code, the phone client scans it | Android / iOS | No |
| [One-click web sign-in](#one-click-web-sign-in-sign-in-to-client) | Click "Sign in to client" in the web panel to open the local client | macOS / Windows; also works in a phone browser | No |
| [Copy login link](#copy-login-link) | Copy a link in the web panel, paste it on the device | Devices that can't scan, such as OpenWrt | No |
| [Telegram Mini App](#telegram-mini-app-sign-in) | Click "Sign in to client" in the bot's Mini App | Users with Telegram bound | No |

The last four all use the same kind of one-time login code, with the same rules:

- **Valid for 5 minutes, single use**; it's void once used. If it expires, click "Regenerate".
- Codes live only in the master's memory, so **a master restart voids all of them**.
- No 2FA code is needed: you, already signed in on the web, are the one authorizing it. That's also why you should **never send the QR code or login link to anyone else** — whoever uses it within 5 minutes is signed in as you.

### Account sign-in

1. Open the "Me" page in MeowX (on macOS, the menu bar panel) and tap "Account sign-in".
2. For "Master address", enter the master server address, e.g. `https://panel.example.com`; then the username and password.
3. If the account has two-factor authentication, you'll be asked for a "Verification code / recovery code": enter the 6-digit code from your authenticator app or one of your backup recovery codes.

Account sign-in isn't affected by the web human verification (Turnstile), but it is subject to [login rate limiting](#login-locked-out).

### QR sign-in

1. Sign in to the panel on a computer, click the avatar at the top right → "QR login". A QR code with a countdown appears.
2. Open MeowX on your phone, tap "Scan to sign in" on the "Me" page and point it at the QR code.
3. Once the client is signed in, just close the web dialog (the web page doesn't detect that the phone has signed in).

If the dialog notes that the phone will connect to some other domain (the master's public address), that's because you opened the panel via a different address (an IP, an internal address, etc.). The phone always connects to the master server address, which is expected.

### One-click web sign-in ("Sign in to client")

For signing in on the computer that already has MeowX installed:

1. Open the "QR login" dialog and click "Sign in to client".
2. The browser asks whether to open MeowX; allow it and the client finishes signing in.

If you're still on the web page about 1.5 seconds later, a toast says no MeowX client was detected. Make sure MeowX is installed on this machine, or that the browser didn't block the request to open an app (try another browser, or allow the site to open external apps).

### Copy login link

For devices like OpenWrt routers that can neither scan nor be launched from the browser:

1. In the "QR login" dialog, click "Copy login link". If copying fails, the link is shown in an input box below; copy it by hand.
2. Paste the link into the device's MeowX within 5 minutes. For the OpenWrt build, paste it into the "Panel Account" card under LuCI "Services → MeowX" → "App Config".

The link looks like `miaomiaowu://login?host=https://panel.example.com&code=…`, where `host` is the master server address and `code` is the one-time login code.

### Telegram Mini App sign-in

Available when the panel has a Telegram bot configured and the user has bound their Telegram account in the panel:

1. Open the bot's Mini App in Telegram. The home page has a "MeowX client" card; tap "Sign in to client".
2. Telegram's in-app browser can't open custom links, so you're taken to an "Opening MeowX" hand-off page; tap "Open MeowX client" there.
3. If it still doesn't open, make sure MeowX is installed, then use the browser menu's "Open in Safari / browser" and try again.

If you see a message that this Telegram account isn't bound to a panel account, complete the Telegram binding in the panel first.

## After signing in

### My subscriptions

"My subscriptions" in the client lists every subscription under the account; tap one to download it and switch to it:

- Regular users: subscriptions assigned by the admin, package subscriptions, their own subscriptions, and the merged subscription.
- Admins: all subscription files, plus packages under their own name.

When the account has exactly one subscription and the device hasn't imported one from this master yet, some platforms import that one automatically.

### Automatic sync

After sign-in, the client keeps an encrypted long-lived connection to the master. When the admin changes nodes, packages or subscriptions, the master tells the client to re-fetch immediately; while the connection is down, the client also checks for updates periodically. The health list of [forwarding](/docs/en/forward) entries is pushed over this connection too, so entry switches don't wait for DNS.

Each account can have at most 16 such connections at once, web tabs included. A few devices plus a few browser tabs per person won't normally hit the limit.

### Session lifetime and signing out

- A sign-in is valid for **30 days** and isn't extended automatically. When it expires the client says the session is no longer valid; just sign in again.
- When a session expires the client only clears the sign-in, **without deleting subscriptions**: the config in use keeps working, and signing in again restores sync.
- Tapping "Sign out" in the client **first deletes the subscriptions imported from this master**, then clears the sign-in (the master address is kept for next time).
- Signing out only affects this device; the session on the master stays valid until it expires. To sign someone out of every device right away, **disable the user** in User Management: the master revokes all their sessions and disconnects all their clients. When an admin changes their own admin credentials, the master invalidates every session site-wide. Kicking out a single device isn't supported yet.

### Login notifications

With "Login notification" turned on in the notification section of System Settings, every sign-in (including client sign-ins) sends a notification with the username and IP address.

## Security model

The client doesn't use the web login flow; it sets up a dedicated encrypted channel with the master:

- **No impersonation**: the master's client identity certificate is issued by the license service and binds the master's domain to a dedicated public key. Before connecting, the client verifies the certificate's signature and checks that its domain matches the domain being connected to; otherwise it refuses. A fake master someone set up, or a hijacked connection, can't produce this certificate.
- **No eavesdropping, no replay**: every request is encrypted with a one-time ephemeral key and carries a timestamp and a nonce. The master only accepts requests within **2 minutes** of its own clock, and the same request can't be replayed. So **a phone with the wrong time will also fail to sign in**.
- **Narrow permissions**: this channel only exposes sign-in, subscriptions and regular user APIs; no admin API is reachable. Even if a client device is lost, all it can do is what a regular user can do.
- Web human verification (Turnstile) doesn't apply to client sign-in, but [login rate limiting](#login-locked-out) still does, and redeeming login codes is rate limited too.

## Troubleshooting

### The web dialog says the master has no usable client identity certificate

The QR sign-in dialog shows no QR code and gives a reason:

| Reason | Fix |
| --- | --- |
| No public domain configured | Fill in the public HTTPS domain under System Settings → "System" → "Master server address" |
| `license is not configured` | Activate the license |
| `certificate domain is claimed by another license` | The domain is bound to another license; use another domain, or contact support to unbind it |
| Other issuance failures (license service unreachable, etc.) | The master retries automatically (up to every 30 minutes); check that the master can reach the internet, or restart it later and try again |

### The client says it can't fetch the master certificate (HTTP 4xx / 5xx)

The client reached the domain but didn't get a certificate. Common causes:

- The reverse proxy, CDN or Cloudflare Tunnel isn't forwarding `/api/secure/*` to the master (returns 404 or a block page). Check in a browser as described in [Checking that the certificate is OK](#checking-that-the-certificate-is-ok).
- The master address entered in the client isn't the master server address (e.g. a subscription domain, an IP, or an internal address). Change it to the master server address's domain.
- The master never obtained a certificate (see the previous item).

### "Certificate domain mismatch" or "certificate expired"

The client checks the certificate domain against the domain it connects to. Signing in via an IP, another domain or an internal address is rejected: for account sign-in, change "Master address" to the master server address. After changing the master server address, old QR codes / links are void; just regenerate them (the certificate is reissued for the new domain).

"Expired" usually means the master has failed to renew for a long time (license invalid, or the master can't reach the license service). Troubleshoot as in [the section above](#the-web-dialog-says-the-master-has-no-usable-client-identity-certificate), then restart the master.

### The QR code is no longer valid

The login code expired (over 5 minutes), was already used, or the master restarted in the meantime. Go back to the web dialog and click "Regenerate".

### `invalid credentials`

Wrong username or password, or the account has been disabled.

### Login locked out

You get `too many login attempts, please try again later`: too many failures from the same IP or account triggered login rate limiting. By default, 5 failures within 60 minutes lock sign-in for 60 minutes.

- An admin can click "Unlock" in the "Login lockouts" list under Logs → "Security log".
- Thresholds are under System Settings → "Security" → "Login rate limit" (max attempts / window / lockout duration).

### `stale request`, or sign-in keeps failing for no clear reason

The phone or computer clock differs from the master's by more than 2 minutes. Turn on automatic time in the system settings and try again; the master server's clock should also be kept in sync.

### Wrong 2FA code

`invalid 2FA code`: check that your authenticator app's clock is correct, or use a backup recovery code instead. `invalid or expired 2FA token` means more than 5 minutes passed before the code was entered; sign in with your password again.

### "Disable public access" is on

With it on, accessing the master via any address other than the master server address redirects to the master server address. Using the master server address's domain in the client, as described above, signs in normally. See [Master Domain](/docs/en/domain-master).
